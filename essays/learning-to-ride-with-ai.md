Earlier today, I read <a href="https://www.anthropic.com/institute/econ-scenarios" target="_blank" rel="noopener noreferrer">Anthropic's Scenarios for our Economic Future</a>, which looks at several possible ways AI could affect work through 2030. One part that stood out to me was its treatment of jobs as collections of tasks. AI may assist with some tasks, automate others, leave some unchanged, and create new ones. In Anthropic's more transformative scenarios, knowledge work is especially affected. One scenario assumes AI becomes capable of doing half of all knowledge work by 2030, while its extreme scenario considers a world where AI performs nearly all knowledge-work tasks autonomously. Anthropic makes it clear that these are scenarios rather than predictions, but they made me think more seriously about what I actually want to learn from a software engineering degree.

Professor Brook compared using AI to riding an electric bicycle: if you don't know how to ride a bicycle, adding a motor won't solve the problem. I agree with the point behind that analogy, especially from my own experience building software with LLMs before fully understanding the code underneath it. At the same time, I think the analogy is becoming more complicated. Someone entering programming today may start on the electric bicycle and never spend much time on the traditional one first. AI-assisted development is already part of how I learned to build things. To me, the important question isn't whether AI should come before or after learning the fundamentals, but whether I'm actually learning to control it, recognize when something is going wrong, and eventually make decisions without depending completely on the assistance. This is coming from my 22-year-old self's perspective, and I try to stay aware that there's a lot I don't know about the industry. I can be wrong about things I've said or written here, but I am trying to figure out how to navigate an AI-augmented world as someone pursuing software engineering.

I think that's where my interests in software engineering are becoming clearer. I want to get better at reading unfamiliar code, debugging problems without immediately asking an LLM for the answer, understanding how different parts of a system interact, and evaluating generated code instead of assuming that working code is correct code. I'm also interested in security and deployment because my own projects have shown me that problems don't stop at the source files. Anthropic's scenarios make those skills feel more important to me. If generating code becomes increasingly automated, I want to understand the parts of software engineering that involve deciding what should be built, determining why something failed, verifying that a solution is safe, and taking responsibility for the result.

The experiences I want next are ones that force me to practice those skills instead of only reading about them. I want more experience maintaining software after it's been deployed, working in a team where someone else reviews my code, reading code written by people other than myself or an LLM, and taking on projects that I can eventually explain from beginning to end. I don't know what software engineering employment will look like several years from now, and Anthropic's own model touches on that uncertainty as well. What I can control is whether I leave school only knowing how to produce software with AI, or whether I also develop enough understanding and judgment to know what that software is doing and when I should not trust it.
